# 引擎升级：QiLin 3.0.7 → 3.0.10（产品 2.0.0-rc.3）与克隆可弃化

日期：2026-10-03
状态：已实施并落盘（KStock 侧本地提交，未推送；QiLin 分支 `kstock/3.0.10`
本地已建、**未推送**——沿用 2026-10-03 迁移时的「不自动推 GitHub」决定）
收口：引擎克隆最终 `--prune` 删除，`vendor/` = 8.2 M（只剩 `skills`）

## 起因

1. 麒麟已发布 **3.0.10**（tag `v3.0.10` → `994f8afd68`，含 v3.0.8–v3.0.10 共
   **98 个提交**）；KStock 随之升 **2.0.0-rc.3**。
2. 迁移到 fork 分支形态后，引擎克隆成了**工作副本**却仍常驻磁盘：
   `vendor/qilin` 3.5 GB（node_modules 1.9 G / .git 277 M / packages 201 M /
   apps 24 M）。用户要求：升级的同时删掉这个目录。

## 一、换基座重放（升级动作）

```bash
cd vendor/qilin
git fetch qilin-dev --tags                       # 本地源仓（离线取 v3.0.10）
git checkout -b kstock/3.0.10 kstock/3.0.7
git rebase --onto 'v3.0.10^{commit}' 'v3.0.7^{commit}' kstock/3.0.10
```

- 7 个提交全部零冲突重放；新旧 7 文件 delta 逐字一致（**7 文件 +105/−9**）。
- 只有 K03 的目标文件被上游改过：`scripts/verify-runtime-closure.ts` 的
  `missingPresetPlugins` 由 async 改同步（改动点在锚点下方 30 行以外），
  `AGENT_PRESET_GLOB` 那一段逐字未动。
- rebase 会把 committer 时间改成当前时刻（author 时间保留）——这正是下面必须
  用 bundle 而非 mbox 做逐位重建的原因。

## 二、锚点更新（唯一事实源）

`upstream.lock.json`：`branch=kstock/3.0.10`、`commit=2b4a533cb0`、
`base_tag=v3.0.10`、`base_commit=994f8afd68`、`version=3.0.10`、
`product_commits=7`、`patches[].commit` 七条全部换新。

| 补丁 | 新提交 |
|---|---|
| K01 `repairStagedScope` | `27b4a90710` |
| K02 install-lefthook 容忍 | `843977301c` |
| K03 preset glob 扩展 | `5ce0dc1728` |
| K04 版本徽章覆盖口 | `4530bd0967` |
| K05 外链 frame-check | `ac85720225` |
| K06 设置分区图标 | `a72941485c` |
| K07 品牌行拆行 | `2b4a533cb0` |

重放物两份（同一序列）：

- `upstream/patches/kstock-3.0.10.patch`（mbox，19.5 KB）——人工审阅 / 逐条重放。
- `upstream/patches/kstock-3.0.10.bundle`（`git bundle`，**9.5 KB**）——逐位重建。

**为什么新增 bundle**：mbox 只带 author 时间，`git am` 的 committer 时间是重放
时刻，重建出的提交号必然不同（实测 `e4ac7547` ≠ `2b4a533c`），契约断言 2
（`HEAD == lock.commit`）会红。bundle 带提交对象，`git fetch <bundle>` 还原出的
HEAD 与 `lock.commit` 逐位一致，前提是克隆里已有基线对象。

## 三、克隆可弃化

`scripts/engine-bootstrap.sh` 增两处：

1. `--prune`：删除克隆目录（有路径与「必须是 git 仓库」双守卫），释放约 3.5 GB。
2. 克隆失败兜底：先试 `git clone --branch kstock/3.0.10`；失败（分支未推送）就
   「克隆远端默认分支（基线对象在它的历史里）→ `git fetch <bundle>` 建分支 →
   checkout 锁定提交」。两者都不可用才提示推分支。

配套：`verify_package_resources.py` 的「闭包引擎版本」改为读
`upstream.lock.json` 的 `engine.version`（克隆在场时再交叉核对
`vendor/qilin/package.json`，抓「lock ↔ 克隆漂移」）——闭包校验不再依赖克隆在场。

### 7.1 只有 CI 才会暴露的两个真问题

**(1) 分支基座与上游 release 标签不一致 → 契约门拦下**

QiLin 的 `v3.0.10` 指向 `206a48dab3`，而本分支基座停在它的父提交
`994f8afd68`（标签落定前的 2 个 `fix(ci)` 提交：`ci-main.yml` 单车预算、
subprocess/workspace-git 两处测试、`prepare-ci-bubblewrap.sh`、
`verify-npm-install-layout.ts`）。上一轮升级时标签尚未落在该提交上，契约断言
`v3.0.10 → base_commit` 因此响亮失败——正是「锚定发布物」要拦的情形。

按升级路径换基座重放：`git rebase --onto 206a48dab39a 994f8afd68a0
kstock/3.0.10`（7 个提交**零冲突**，与那 2 个提交的改动面零交集）→ 刷新
`upstream.lock.json`（`base_commit` / `commit` / `patches[].commit` 七条）→
重导出 `upstream/patches/kstock-3.0.10.{patch,bundle}` → 契约 13/13。

**并且必须把分支推上去**：远端旧 tip `2b4a533cb0` 仍在，而 CI 的
`engine-bootstrap.sh` 只有在**克隆失败**时才走 bundle 兜底；克隆成功但
`lock.commit` 不在对象库里是直接 `die`。故 `--force-with-lease` 推送
（`2b4a533cb0 → e2dfa514d0`）。

**(2) macOS runner 的 bash 3.2 + UTF-8 locale：`$VAR（` 被并进变量名**

首次把「引擎克隆」作为 CI 步骤下发后，`release.yml` 的 macOS 作业在该步
**0.76 秒**即失败：

```
scripts/engine-bootstrap.sh: line 123: REPO?: unbound variable
```

根因不是网络也不是分支未推送：bash 3.2 在 UTF-8 locale 下把紧跟 `$VAR` 之后
的多字节字符（「（」= `EF BC 88`）当作标识符字节并进变量名，于是
`"…：$REPO（$BRANCH）"` 里的 `$REPO（` 变成未定义变量 `REPO（`，`set -u`
当场致命。**本机永远绿**是因为本机 `LC_CTYPE=C`：

```bash
# 100% 复现（本机 /bin/bash 就是 3.2）
env -i PATH=/usr/bin:/bin LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 \
  /bin/bash -uc 'REPO=x; echo "$REPO（"'
# → REPO?: unbound variable
```

修法：12 处一律写 `${VAR}`（花括号显式界定变量名）。

### 7.2 固化：脚本可移植性门禁

新增 `scripts/verify_shell_portability.py`，接入 `check-ci.sh` **全量段**（→
prepush 与 `ci.yml` 都跑；`audit.mjs` 的 `--types-only` 段保持纯类型，不被稀释）：

| 检查 | 覆盖 | 验证证据 |
|---|---|---|
| `$VAR` 紧邻非 ASCII 静态扫描（跨平台、与 locale 无关） | 全仓 tracked shell 脚本 | 正向：18 个脚本 0 违例；**反向**：对 `4be238be`（出事的 commit）worktree 跑 → **exit 1**，精确命中 10 行、含 CI 报错第 123 行 |
| `/bin/bash` 为 3.x 时，UTF-8 locale 下逐脚本 `bash -n` | macOS（Linux/Windows 的 bash 5.x 解析口径与 ubuntu 车道一致，跳过） | 18 个脚本 0 处语法失败；`bash -n` 全脚本扫描同时确认无 bash 4 专属内置命令 |

**教训（值得写进发版检查表）**

1. 只在**新增的 CI 路径**上执行的 shell 分支（本轮的「引擎克隆引导」就是），
   提交前必须在「模拟 runner 的 shell + locale」下跑一遍——本地 shell/locale
   与 runner 不一致时，本地绿毫无信息量。
2. 变量引用一律 `${VAR}`；宁可多两个花括号。
3. 门禁脚本自身要有**反向验证**（对新门禁跑一次已知会失败的旧树），否则只是
   装饰。

## 八、门禁补强：闭包产物 commit 比对（2026-10-03 12:35 +08）

**缺口（本轮暴露）**：`scripts/verify_package_resources.py` 的产物模式只比对
`.runtime-version` 的 `version`。而 **同版本号换基座** 时 version 完全相同——
本轮 v3.0.10 的基座就从 `994f8afd` 换到了 `206a48da`——于是「换基座前构建的
staging（`3.0.10` + `2b4a533cb0`）」会被 **version 比对静默放行**，然后打进
安装包。`check-release.sh` 恰好每次都会先重建，所以本次发行没出事，但
`build-desktop.sh` 直跑这条路（以及「本地已有旧产物、不想等重建」的用法）
没有任何拦截。

**修法**：新增 `product closure engine commit` 断言，事实源
`upstream.lock.json`（`engine.commit`，与 version 同一权威）。三态明确：

| 产物 `.runtime-version` | 判定 |
|---|---|
| `commit` == `lock.engine.commit` | `[OK] product closure engine commit = <短号>` |
| `commit` 不等 | `[FAIL]` + 两侧短号 + 「重建：`bash scripts/build-runtime-bundle.sh`」 |
| 缺 `commit` 字段（早于 commit 追踪的产物） | `[FAIL]`（**不是**静默通过） |

比对容忍任一侧写合法缩写（≥7 位）与大小写/空白差异——lock 侧若手工改成短号
不产生假红。克隆在场时的「克隆 `HEAD` == `lock.commit`」仍由
`verify_engine_contract.py` 负责，此处不重复。

**验证证据**（全部夹具驱动：引擎克隆已 `--prune`、真 staging 已删，因此不依赖
任何重产物）：

| 验证 | 结果 |
|---|---|
| 夹具矩阵（7 用例：命中 / 换基座旧产物 / 缺字段 / lock 短 SHA / 大小写空白 / 版本+commit 双漂移 / marker 非法 JSON） | **7/7 符合期望** |
| 真实 `upstream.lock.json` + 空壳 staging 跑**产物模式 CLI** | `[OK] product closure engine version = 3.0.10` + `[OK] … commit = e2dfa514d027` |
| 同上，把 marker 改成换基座前的 `2b4a533cb0…`（**本轮要拦的场景**） | `[OK] version` + **[FAIL] `product closure engine commit`**，detail 指名两侧短号 |
| `py_compile` / 生产代码路径 | 通过；改动只落在产物段 |

**注意**：`--source-only`（`check-ci.sh` 走的模式）**不跑**产物段，所以这道闸门
只在 `check-release.sh` 与打包前生效——与 version 比对完全同一条路径，无新增
调用点。`docs/开发/发布契约.md` §1 单一事实源表已同步登记该「版本 + 提交」事实。

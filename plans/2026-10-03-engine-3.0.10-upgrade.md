# 引擎升级：QiLin 3.0.7 → 3.0.10（产品 2.0.0-rc.3）与克隆可弃化

日期：2026-10-03
状态：已实施并落盘（KStock 侧本地提交，未推送；QiLin 分支 `kstock/3.0.10`
本地已建、**未推送**——沿用 2026-10-03 迁移时的「不自动推 GitHub」决定）
收口：引擎克隆最终 `--prune` 删除，`vendor/` = 8.2 M（只剩 `skills`）

## 起因

1. 麒麟已发布 **3.0.10**（tag `v3.0.10` → `994f8afd68`，含 v3.0.8–v3.0.10 共
   **98 个提交**）；KStock 随之升 **2.0.0-rc.3**。
2. 迁移到 fork 分支形态后，引擎克隆成了**工作副本**却仍常驻磁盘：
   `vendor/qilin` 3.5 GB（node_modules 1.9 G / .git 277 M / packages 201 M /
   apps 24 M）。用户要求：升级的同时删掉这个目录。

## 一、换基座重放（升级动作）

```bash
cd vendor/qilin
git fetch qilin-dev --tags                       # 本地源仓（离线取 v3.0.10）
git checkout -b kstock/3.0.10 kstock/3.0.7
git rebase --onto 'v3.0.10^{commit}' 'v3.0.7^{commit}' kstock/3.0.10
```

- 7 个提交全部零冲突重放；新旧 7 文件 delta 逐字一致（**7 文件 +105/−9**）。
- 只有 K03 的目标文件被上游改过：`scripts/verify-runtime-closure.ts` 的
  `missingPresetPlugins` 由 async 改同步（改动点在锚点下方 30 行以外），
  `AGENT_PRESET_GLOB` 那一段逐字未动。
- rebase 会把 committer 时间改成当前时刻（author 时间保留）——这正是下面必须
  用 bundle 而非 mbox 做逐位重建的原因。

## 二、锚点更新（唯一事实源）

`upstream.lock.json`：`branch=kstock/3.0.10`、`commit=2b4a533cb0`、
`base_tag=v3.0.10`、`base_commit=994f8afd68`、`version=3.0.10`、
`product_commits=7`、`patches[].commit` 七条全部换新。

| 补丁 | 新提交 |
|---|---|
| K01 `repairStagedScope` | `27b4a90710` |
| K02 install-lefthook 容忍 | `843977301c` |
| K03 preset glob 扩展 | `5ce0dc1728` |
| K04 版本徽章覆盖口 | `4530bd0967` |
| K05 外链 frame-check | `ac85720225` |
| K06 设置分区图标 | `a72941485c` |
| K07 品牌行拆行 | `2b4a533cb0` |

重放物两份（同一序列）：

- `upstream/patches/kstock-3.0.10.patch`（mbox，19.5 KB）——人工审阅 / 逐条重放。
- `upstream/patches/kstock-3.0.10.bundle`（`git bundle`，**9.5 KB**）——逐位重建。

**为什么新增 bundle**：mbox 只带 author 时间，`git am` 的 committer 时间是重放
时刻，重建出的提交号必然不同（实测 `e4ac7547` ≠ `2b4a533c`），契约断言 2
（`HEAD == lock.commit`）会红。bundle 带提交对象，`git fetch <bundle>` 还原出的
HEAD 与 `lock.commit` 逐位一致，前提是克隆里已有基线对象。

## 三、克隆可弃化

`scripts/engine-bootstrap.sh` 增两处：

1. `--prune`：删除克隆目录（有路径与「必须是 git 仓库」双守卫），释放约 3.5 GB。
2. 克隆失败兜底：先试 `git clone --branch kstock/3.0.10`；失败（分支未推送）就
   「克隆远端默认分支（基线对象在它的历史里）→ `git fetch <bundle>` 建分支 →
   checkout 锁定提交」。两者都不可用才提示推分支。

配套：`verify_package_resources.py` 的「闭包引擎版本」改为读
`upstream.lock.json` 的 `engine.version`（克隆在场时再交叉核对
`vendor/qilin/package.json`，抓「lock ↔ 克隆漂移」）——闭包校验不再依赖克隆在场。

## 五、已知缺口 / 待办

1. **分支未推 GitHub（tag `v3.0.10` 已推）**：`ci.yml` / `release.yml` 都先跑
   `engine-bootstrap.sh`——推了分支就是正常克隆，没推则走 bundle 兜底（基线对象
   从远端 `main` / tag 取，实测通过）；推分支命令：
   `git -C vendor/qilin push origin kstock/3.0.10`（需先引导回克隆）。
2. **staging 是 3.0.7 旧闭包**：`staging/kstock-runtime/.runtime-version` =
   `{version: 3.0.7, commit: c375a80f}`。发布链 `check-release.sh` 会先跑
   `build-runtime-bundle.sh` 重建；**直接跑 `build-desktop.sh` 之前必须重建**，
   否则把 3.0.7 闭包打进包（闭包版本校验会拦）。
3. **dist-exe 是 3.0.7 遗留产物**（406 MB）：`engine.ts` dev 首选「单文件 exe +
   `--help` 冒烟通过」→ 删掉克隆后它仍会被优先使用，等于本地 dev 静默跑 3.0.7
   引擎。要么删掉（dev 会 fail-loud 提示引导），要么重建。
4. `--prune` 之后再跑门禁 / 类型检查（`check-ci.sh`、`kstock/*` 的 tsc）需要
   重新引导：tsconfig `paths` 指向 `vendor/qilin/packages/**/src`。

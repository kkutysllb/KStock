# 引擎分支工作流（QiLin fork + 锁定提交）

> KStock 与 QiLin 引擎之间是**「进程 + 编译期路径映射 + 可再生产物」边界**，
> 不是「源码编译」边界。引擎源码不再 vendor 进本仓；产品对引擎的定制全部是
> QiLin fork 分支 `kstock/<基线>` 上的提交。

## 形态总览

| 凭据 | 位置 | 是否入库 | 作用 |
|---|---|---|---|
| 分支与提交 | `upstream.lock.json` 的 `engine` 段 | ✅ 入库 | **唯一事实源**：repo / branch / commit / base_tag / base_commit / version / 7 处补丁清单 |
| 克隆点 | `vendor/qilin` | ❌ 整目录 gitignore | 引擎的 git 克隆（含 `.git`、`node_modules`、`lib`，约 3.5 GB）；**按需引导、用完可删**（`--prune`），门禁与构建前重新引导即可 |
| 重放物（人工审阅） | `upstream/patches/kstock-3.0.10.patch` | ✅ 入库 | 同一提交序列的 mbox（`git format-patch`），供人工审阅与逐条重放 |
| 重放物（逐位重建） | `upstream/patches/kstock-3.0.10.bundle` | ✅ 入库 | `git bundle`（9.5 KB）——带 7 个提交**对象**，重建出的 HEAD 与 `lock.commit` 逐位一致 |
| 契约校验 | `scripts/verify_engine_contract.py` | ✅ 入库 | 把「磁盘上这棵树是什么」变成一组可执行断言 |
| 引导入口 | `scripts/engine-bootstrap.sh` | ✅ 入库 | 克隆 / 更新 / 落到锁定提交 / 校验 / 可选装依赖与构建 |

KStock 消费引擎的四个面（都不需要源码入库）：

1. **编译期**：`kstock/client-brand/tsconfig.json` 的 8 条 `paths` 映射指向
   `vendor/qilin/packages/**/src`（类型解析）——所以克隆点固定在 `vendor/qilin`，
   路径与旧快照形态逐字一致。
2. **构建期**：`scripts/qilin-pnpm.sh`（钉 pnpm 11.7.0）在 clone 里跑
   `install / run build / run verify-runtime-closure`。
3. **运行期**：`profile-bundles.ts` 五层叠层 + cordis slots 消费引擎面；
   打包态跑 `staging/kstock-runtime` 闭包。
4. **打包期**：`pnpm deploy` 把引擎生产闭包物化成 `staging/kstock-runtime.tar.gz`。

## 日常命令

```bash
bash scripts/engine-bootstrap.sh            # 克隆/更新 + 契约校验（默认，不装依赖）
bash scripts/engine-bootstrap.sh --check-only    # 只校验（不联网、不改动）
bash scripts/engine-bootstrap.sh --full          # 校验 + install + build + 闭包门禁
bash scripts/engine-bootstrap.sh --build         # 只补构建（改了引擎源码后）
bash scripts/engine-bootstrap.sh --prune         # 删除克隆释放磁盘（约 3.5 GB）
python3 scripts/sync_upstreams.py --refresh-lock # 刷新 lock 的 branch/commit/version
```

克隆是**可弃的**：`.git`、`node_modules`、`lib` 全部不需要长期留在磁盘上。
`--prune` 删掉整个 `vendor/qilin`（含未推送的本地分支——定制已固化在
`upstream/patches/*.patch` 与远端分支里），下次需要构建或跑门禁时重新
`engine-bootstrap.sh`（约 1–3 分钟克隆 + 依赖安装 + 构建）。同理，任何
`check-ci.sh` / `check-release.sh` / `kstock/*` 类型检查都要求克隆在场
（tsconfig `paths` 指向 `vendor/qilin/packages/**/src`），先引导再跑。

`scripts/qilin-pnpm.sh` 每次调用前都会断言
`git -C vendor/qilin rev-parse HEAD == lock.engine.commit`；不等即拒绝执行
（逃生口 `KSTOCK_ENGINE_ALLOW_DIRTY=1`，仅诊断用）。

## 契约：`verify_engine_contract.py` 断言什么

| # | 断言 | 拦住的失败 |
|---|---|---|
| 1 | 克隆存在且是 git 仓库 | 忘了引导 / 目录被删 / 误放成普通目录 |
| 2 | `HEAD == engine.commit` | 克隆被切走、被就地改过 |
| 3 | `engine.base_tag` → `engine.base_commit` 一致 | lock 自相矛盾 |
| 4 | `base_commit` 是 `HEAD` 的祖先 | 换基线时在旧基线上偷偷叠加 |
| 5 | `base_commit..HEAD` 提交数 == `len(engine.patches)` | 集成分支被追加/删除提交（裸提交） |
| 6 | 每条补丁：提交在 HEAD 历史内 + 目标文件里标记仍在 | **上游重构吃掉本地定制** |
| 7 | 工作树无未提交的已跟踪改动（告警；`--strict-clean` 转失败） | 直接改 clone 源码而不落提交 |

第 6 条是这套形态的核心价值：补丁 14（`repairStagedScope`）、15、21、22
历史上都丢过或差点丢掉，且丢法全是**静默**的。标记断言把「定制是否还在」
从「祈祷」变成「构建第一个红」。

跑在发布链上的位置：`check-ci.sh` 由 CI 步骤显式 bootstrap 后执行；
`build-engine-bundle.sh` 与 `build-runtime-bundle.sh` 都在**第一步**跑
`engine-bootstrap.sh --check-only`（历史教训 B3：补丁 14 曾在步骤 3 才重放，
导致 Windows staging 修复从未参与单文件构建）。

## 加一处新的引擎定制

```bash
bash scripts/engine-bootstrap.sh --check-only          # 先确认在锁定态
cd vendor/qilin
git checkout kstock/3.0.10                             # 确认在分支上（非 detached）
# …改文件…
git commit                                             # 提交信息写清症状/根因/修法
cd ../..
# 1) 更新 lock：engine.commit / branch / version（基线三件套不动）
python3 scripts/sync_upstreams.py --refresh-lock
# 2) 手工补 engine.patches 一条（id / commit / file / marker / title）
#    并同步 engine.product_commits
# 3) 重新导出提交序列（mbox 供审阅 + bundle 供逐位重建）
git -C vendor/qilin format-patch --no-signature --stdout \
  'v3.0.10^{commit}'..HEAD > upstream/patches/kstock-3.0.10.patch
git -C vendor/qilin bundle create "$PWD/upstream/patches/kstock-3.0.10.bundle" \
  'v3.0.10^{commit}'..HEAD
# 4) 校验 + 全量回归
bash scripts/engine-bootstrap.sh --check-only
bash scripts/check-ci.sh
```

`marker` 要选**该补丁独有、且上游不可能碰巧出现**的字符串（现有 7 条的
marker 都在代码里以 `KStock patch:` 注释形式随补丁落进分支）。

## 升级到新基线（例：3.0.7 → 3.0.10，2026-10-03 实例）

单条集成分支的升级路径就是「换基座 + 重放提交」：

```bash
cd vendor/qilin
git fetch qilin-dev --tags                 # 本地源仓（离线）；联网时 git fetch origin --tags
git checkout -b kstock/3.0.10 kstock/3.0.7
git rebase --onto 'v3.0.10^{commit}' 'v3.0.7^{commit}' kstock/3.0.10
# 逐个解决锚点漂移——上游重构了锚点就在这里表现出来（fail-loud）
cd ../..
# 更新 lock：branch / commit / base_tag / base_commit / version /
#           patches[].commit / product_commits / patch_series
git -C vendor/qilin format-patch --no-signature --stdout \
  'v3.0.10^{commit}'..HEAD > upstream/patches/kstock-3.0.10.patch
git -C vendor/qilin bundle create "$PWD/upstream/patches/kstock-3.0.10.bundle" \
  'v3.0.10^{commit}'..HEAD
git rm upstream/patches/kstock-3.0.7.patch upstream/patches/kstock-3.0.7.bundle
# lock 同步：patch_series / patch_bundle 指向新文件
bash scripts/engine-bootstrap.sh --check-only     # 13 项断言必须全绿
bash scripts/engine-bootstrap.sh --full           # install + build + 闭包门禁
bash scripts/check-ci.sh && bash scripts/check-release.sh
```

`git rebase --onto` 一次重放 7 个提交；本次（3.0.7 → 3.0.10，98 个上游提交）
只有 K03 的目标文件被上游改过（`verify-runtime-closure.ts` 的
`missingPresetPlugins` 由 async 改同步，改动点在我们锚点下方 30 行以外），
rebase 零冲突、7 处标记全在。

升级的 7 处锚点清单（新基线上逐个核对）：

| 补丁 | 文件 | 关注点 |
|---|---|---|
| K01 | `scripts/build-exe-for-python-sdk.ts` | `materializeStagedLinks()` 调用点与 staging 清单方法头 |
| K02 | `scripts/install-lefthook.mjs` | lefthook 静态导入与 `main()` 守卫 |
| K03 | `scripts/verify-runtime-closure.ts` | `AGENT_PRESET_GLOB` 常量 |
| K04 | `scripts/client-build-environment.ts` | `repositoryClientBuildEnvironment` 返回体 |
| K05 | `packages/client/ui-chat/src/client/apply.ts` | `openExternalLink` 的 `linkOpening` 判定块 |
| K06 | `packages/client/ui-settings-general/src/client/SettingsRoot.tsx` | 值导入块收尾序列 + `navIcon` 映射 |
| K07 | `packages/client/ui-sidebar/src/client/SidebarRoot.module.css` | `.topStrip` 高度与 `.topStrip + .logoRow` 规则 |

## 失败处置

| 症状 | 原因 | 处置 |
|---|---|---|
| `qilin-pnpm: 引擎克隆 HEAD xxxx != upstream.lock.json 的 yyyy` | 克隆被切走或刚提交了新补丁 | 跑 `engine-bootstrap.sh`，或提交后 `--refresh-lock` |
| `K0N 补丁标记丢失` | 上游重构了该处（锚点漂移） | 在新形态上重做该提交，更新 `patches[].marker` |
| `产品提交数 N != lock 的 7` | 分支被追加/回退提交 | 补齐 `engine.patches` 与 `product_commits`，或回退分支 |
| `基线 … 不是 HEAD 的祖先` | 换了基座但没改 lock | 改 `base_tag`/`base_commit`（升级流程） |
| `克隆失败：…（分支是否已推送？）` | fork 分支还在本地 | 引导脚本会自动退到「远端默认分支的基线对象 + 仓库内 bundle」重建；两者都不可用才需要推分支 `git -C vendor/qilin push origin kstock/3.0.10` |
| `引擎克隆缺失且未引导` / 门禁报 `source vendor/qilin engine CLI` 缺失 | 跑过 `--prune`，或换了机器 | `bash scripts/engine-bootstrap.sh`（需要构建再加 `--full`） |
| 工作树脏告警 | 构建重写了 `THIRD_PARTY_NOTICES.md` 之类产物 | 属预期；若确为源码改动，落成提交而不是留在树里 |

引擎克隆缺失（删过、或新机器）时的两条重建路径：

```bash
bash scripts/engine-bootstrap.sh              # 首选：联网克隆分支；未推送时自动走 bundle

# 手工等价（分支未推送、离线时）：
git clone --single-branch https://github.com/kkutysllb/QiLin.git vendor/qilin
git -C vendor/qilin fetch upstream/patches/kstock-3.0.10.bundle \
  refs/heads/kstock/3.0.10:refs/heads/kstock/3.0.10
git -C vendor/qilin checkout kstock/3.0.10
bash scripts/engine-bootstrap.sh --check-only   # 13 项断言应全绿（HEAD 逐位一致）
```

`git am upstream/patches/*.patch` 仍然可用，但它只带 author 时间、committer
时间会取当前时刻，**重建出的提交号必然不同**（`HEAD == lock.commit` 断言会红），
所以只作人工审阅与无 bundle 时的最后兜底。bundle 才带提交对象，能逐位还原。

## 为什么这么设计（与 KCoder 同源）

1. **边界是进程与路径映射，不是链接。** 桌面壳不声明任何 `@qilin/*` 依赖，
   只经 tsconfig `paths`（编译期）与 profile bundles / slots（运行期）消费
   引擎面；源码在树内不产生编译期收益，只产生合并成本。
2. **上游是可再生产物的提供者。** `pnpm deploy --prod` 能从锁定提交推导出
   整个生产闭包，因此「源码副本」是冗余的，而且必然腐烂。
3. **契约面窄且可断言。** 7 处定制 + 6 类断言（上表）替代了「源码共处」；
   与 KCoder 用 `dsh-contract.ts` + BASELINE 断言守住同一个 12 条锚点清单
   是同一个手法。
4. **多产品共享同一个引擎仓。** QiLin 仓里已有 `lingshu/000N-*` 这类产品
   分支先例；把源码拷进每个产品仓会立刻退化成 N 份互相冲突的分叉。
5. **体积与可追溯性。** 旧快照形态：9423 个文件 / 86.8 MB 入库、且取自
   **上游工作树**（非提交），内容与「哪个提交」并无一一对应。新形态：
   `git ls-files vendor/` 只剩 `vendor/skills`（409 个文件，全仓 848 个），
   引擎侧「这棵树 == 哪个提交」由断言保证；克隆本身是可弃的工作副本
   （`--prune` 删掉约 3.5 GB，bundle 逐位重建）。

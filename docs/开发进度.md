### 关键修复：secrets.env 与引擎热重载

引擎（vendor/qilin）基于 mtime 检测 `qilin.runtime.yaml` 变化并自动重载，重载时通过 `AppConfig.resolve_env_variables` 从进程 `os.environ` 解析 `$KEY` 引用。初版实现把 API key 写进了 secrets.env 文件、却从未加载到 gateway 进程环境，导致 POST 创建含 api_key 的模型后 GET 返回 500（`ValueError: Environment variable KSTOCK_MODEL_X_KEY not found`）。

修复（commit 6bfc835）：

- `run_gateway.py` 新增 `_load_secrets_env`，启动时把已有 secrets.env 加载到 `os.environ`（日志打印加载数量）；
- `kstock_models.upsert_secret` / `remove_secret` 同步更新 `os.environ`，使运行时增删即时生效，引擎下次热重载即可解析新引用，无需重启 gateway。

### 关键发现：真实 SSE 协议

Task 0 实测纠正了 plan 初稿的协议假设：

- 路径是 `/api/threads`（非 `/api/v1/threads`）
- event 名是 `messages`（非 `messages-tuple`）；`messages` 的 data 是数组 `[msg_dict, metadata_dict]`，取 `data[0]`
- `msg_dict.type` 枚举：
  - 非流式快照：`human` / `ai` / `tool` / `system`（非 user/assistant）
  - **流式 chunk**（全 langchain provider）：`AIMessageChunk` / `ToolMessageChunk` / `HumanMessageChunk` / `SystemMessageChunk`。最初只认 `ai`，MiniMax 流式文本不渲染；后重构为**语义优先路由**——不依赖 type 字符串，按语义特征（tool_call_id / reasoning_content / content / tool_calls / usage_metadata）路由，所有 provider 及未来新增自动适配
- system-reminder 带 `additional_kwargs.hide_from_ui=true`，前端跳过
- 引擎把 provider error（如 API key 无效）包装成带 `qilin_error_fallback=true` 的 ai message（而非 SSE error 事件）
- **MiniMax api_base**：国内版 `api.minimaxi.com/v1`，国际版 `api.minimax.io/v1`；key 与域名不匹配会报 AuthenticationError 401

### 架构决策

- **前端直连引擎网关**（零新 BFF）：fetch POST + ReadableStream 读 SSE，不用 EventSource（后者不支持 CSRF header）
- **localStorage 会话真源**：ChatSession 加 `threadId`，首次发消息时 `POST /threads` 创建并绑定
- **RunContext 注入**：`model_name` + `thinking_enabled`（`supports_thinking`）+ `reasoning_effort`（按需）

### 关键修复一：authorization UI 防护（enabled 依赖 provider）

**问题**：用户在 UI 启用「资源授权」但未配 provider，导致 `authorization.enabled=true`
且 `provider=null` 的自相矛盾状态。gateway 每次路由请求报
`ValueError: authorization.enabled is true but no provider is configured`，
日志 WARNING 刷屏。

**修复**（两层）：

1. 止血：把用户 `runtime.yaml` 的 `authorization.enabled` 改回 false；
2. UI 防护：`GuardrailsSettings` 根据 `provider` 状态动态生成字段——provider 为 null
   时，「启用资源授权」开关灰色禁用，下方显示警告「需先在 runtime.yaml 配置
   `authorization.provider.use`才能启用」。

实现要点：
- `RuntimeConfigCard.tsx` 的 `FieldDef` 扩展 `disabled?` + `disabledReason?` 两个
  可选字段，作为通用 UI 能力（不限于 authorization）；
- `FieldRenderer` 在全部 7 种 input 类型（boolean / select / number / string /
  nullable-string / string-list / context-size）传递 `disabled` 属性；
- CSS `.rcf-field.is-disabled`（opacity 0.6）+ `.rcf-disabled-reason`（amber-500
  警告色）。

### 关键修复二：runtime.yaml tools 段增量合并（老用户 yaml 同步）

**问题**：agent 被问「今天 A 股有哪些新闻」时回复「不支持实时网页搜索」，但
`config/qilin.config.yaml` 里明明挂了金融搜索工具。gateway 日志显示
`Total tools loaded: 0`。

**根因**：用户 `runtime.yaml` 是早期版本首次启动时从模板复制的，那时模板还没
`tools:` 段。`_generate_runtime_config` 的策略是「已存在则直接 return，绝不
覆盖」（为了避免覆盖用户持久化的 models / memory / database 配置），但这导致
模板后续新增的 `tools` 段永远到不了老用户 yaml，`config.tools` 为空，LLM 看不
到任何工具。

**修复**：把「已存在则 return」改为「已存在则增量合并模板的 `tools` 段」。
`tools` 段是产品级配置（不是用户级），覆盖安全；其他段仍原样保留。当
`existing.tools != template.tools` 时才写入，保证幂等。

涉及文件：
- `scripts/run_gateway.py` — `_generate_runtime_config` 增量合并逻辑；
- `tests/test_run_gateway.py` — 3 个新回归测试（老 yaml 缺 tools 段 / 模板升级
  后旧引用被覆盖 / tools 已同步时幂等）+ 1 个端到端测试补 tools 断言。

## 阶段七：基础工具注册修复（hotfix）

### 问题现象

agent 执行报告生成任务时报错：
- 「分析报告技能包未直接可用」
- 「当前环境没有 write_file 工具可用」
- 「引擎 run 报错」

### 根因

`config/qilin.config.yaml` 的 `tools` 段只注册了 2 个金融搜索工具（finance_data_search / finance_news_search），**缺少所有基础文件操作和 bash 工具**。这导致连锁反应：

1. **Lead Agent 没有 write_file** → 尝试自己写报告时报「write_file 工具不可用」
2. **技能无法激活** → 技能需要 read_file 读取 SKILL.md 来激活，read_file 不存在形成死锁 → 「技能包未直接可用」
3. **子代理工具引用无效** → chan-theory-analyst / backtest-executor 声明的 bash/read_file/write_file/str_replace 都不存在
4. **最终「引擎 run 报错」**

工具加载机制（`qilin.tools.tools.get_available_tools`）从 `config.tools` 列表加载，不注册就不存在。基础工具的 `use` 路径是 `qilin.sandbox.tools:{tool_name}_tool`（vendor/qilin/qilin/sandbox/tools.py 定义了 ls/read_file/glob/grep/write_file/str_replace/bash 7 个函数）。

另外 `sandbox.allow_host_bash: false` 会过滤掉 bash 工具（`_is_host_bash_tool` 检查），桌面端需要 true。

### 修复

| 功能 | 涉及模块 | 状态 |
|------|----------|------|
| `tools` 段补充 7 个基础工具（ls/read_file/glob/grep/write_file/str_replace/bash） | `config/qilin.config.yaml` | ✅ |
| `sandbox.allow_host_bash` 改为 true（桌面端缠论/回测子代理需要 bash） | `config/qilin.config.yaml` | ✅ |

## 阶段八：技能包目录结构修复（hotfix）

### 问题现象

agent 执行报告生成任务时报错：

```
target: analysis-report
Error: failed to review skill package: ValueError: Local review targets must be .skill archives or directories containing a root SKILL.md
```

同时阶段七的「技能包未直接可用」在补全工具后仍未解决——引擎 `load_skills()` 返回 **0 个技能**。

### 根因

`vendor/skills` 原目录结构为 `stock/<name>/SKILL.md` + `common/<name>/SKILL.md`，但 QiLin 引擎的 `LocalSkillStorage._iter_skill_files()` 只遍历 `SkillCategory` 枚举值对应的子目录：

```python
# vendor/qilin/qilin/skills/storage/local_skill_storage.py L78-80
for category in SkillCategory:                # public / custom / integrations / legacy
    category_path = skills_root / category.value
    if not category_path.is_dir():
        continue
```

`SkillCategory` 的合法值是 `public`/`custom`/`integrations`/`legacy`（见 `qilin/skills/types.py`）。KStock 的 `stock` 和 `common` **不匹配任何 category 值** → 引擎遍历时找不到任何 category 目录 → `load_skills()` 返回空 → 所有技能不可见。

这导致连锁反应：
1. **技能数为 0** → Lead Agent 看不到任何技能 → 「技能包未直接可用」
2. **`skill://` URI 解析失败** → `review_skill_package(target="analysis-report")` 用裸名字找不到技能，用 `skill://` 又缺 category 前缀
3. **子代理声明的 skills 白名单全部无效** → `stock-researcher` 声明 5 个技能但都加载不出来

### 修复

核心思路：把预置技能全部放到引擎认识的 `public` category 下（只读预置技能符合 public 语义）。`stock`/`common` 的分类概念保留为前端展示用的 `group` 标签，从 `approved-skills.json` 的 `kind` 字段读取。

| 改动 | 涉及模块 | 状态 |
|------|----------|------|
| `vendor/skills/{stock,common}/*` → `vendor/skills/public/*`（git mv 保留历史） | `vendor/skills/public/` | ✅ |
| `approved-skills.json` 的 `target_path` 全部改为 `public/<name>`（`source_path` 不变，上游仍是 stock/common） | `vendor/skills/approved-skills.json` | ✅ |
| `_scan_available_skills` 改为扫描 `public/*/SKILL.md`；新增 `_load_skill_kind_map` 从 manifest 读 `kind` 字段提供 `group` 标签 | `scripts/kstock_extensions_config.py` | ✅ |
| `sync_upstreams.py` / `verify_skill_pack.py` 无需改动（已基于 manifest 的 `target_path` 动态读路径） | — | ✅（自动适配） |
| 过时注释更新 | `tests/test_kstock_extensions_config.py` | ✅ |

### 为什么不动 `runtime.yaml` 的 `skills.root`

`skills.root` 仍指向 `vendor/skills`（仓库内绝对路径）。引擎从这个 root 下找 `public/` 子目录，路径正确。无需改动。

### 为什么用 `public` 而不是新增 category

- `public` 在 QiLin 引擎里就是「预置只读技能」的语义，符合 KStock 的产品定位
- 改 `SkillCategory` 枚举需要动 vendor 代码，上游同步时会冲突
- `stock`/`common` 是 KStock 自有的产品分类（前端展示用），不是引擎概念，用 manifest 的 `kind` 字段承载更干净

### 验证

- **引擎技能发现**：`LocalSkillStorage.load_skills()` 返回 **12 个技能**，全部 `category=public, enabled=True`
- **后端 pytest**：118 passed + 3 skipped（无回归）
- **前端 vitest**：254 passed（`SkillsExtensionsCard.spec.tsx` 的 mock 数据用 `"stock"/"common"` 作为 group 字段，组件接收什么 group 就展示什么，不受目录结构影响）
- **`sync_upstreams --sync-skills`**：基于 manifest 的 `source_path`→`target_path` 映射，上游 `stock/xxx` 会自动复制到 `public/xxx`，无需改同步逻辑

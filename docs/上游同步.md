# 上游同步说明

上游有两条线，**形态不同，按对象选工具**：

| 上游 | 形态 | 落点 | 文档 |
|---|---|---|---|
| QiLin 引擎（代码） | **fork 分支的 git 克隆**，不入库 | `vendor/qilin` | [引擎分支工作流](引擎分支工作流.md) |
| KSkills 技能包（数据） | **拷贝快照 + 补丁幂等重放**，入库 | `vendor/skills` | 本文 |

## 本地源仓库

- KSkills：`/Users/libing/kk_Projects/KSkills`

## 引擎（QiLin）

引擎**不再**走「整树拷贝进 vendor」的同步。产品对引擎的 7 处定制是
QiLin fork 分支 `kstock/<基线>` 上的提交，`upstream.lock.json` 的 `engine`
段是唯一事实源（分支 + 锁定提交 + 基线 tag/commit + 补丁清单）：

```bash
bash scripts/engine-bootstrap.sh                  # 克隆/更新 + 契约校验
bash scripts/engine-bootstrap.sh --check-only     # 只校验（不联网）
bash scripts/engine-bootstrap.sh --full           # 再装依赖 + 建产物 + 闭包门禁
python3 scripts/sync_upstreams.py --sync-qilin    # 同上（转发别名）
python3 scripts/sync_upstreams.py --refresh-lock  # 刷新 lock 的 branch/commit/version
```

分支、提交、契约断言、加补丁与升级流程，全部见
**[引擎分支工作流](引擎分支工作流.md)**。

## 技能包（KSkills）

```bash
python3 scripts/sync_upstreams.py --sync-skills
python3 scripts/verify_skill_pack.py
```

规则：

- 只同步批准清单（`vendor/skills/approved-skills.json`）里的技能
- KSkills 同步到 `vendor/skills`，作为产品发布输入（入库快照）
- 不直接修改上游仓库
- 所有产品定制留在 KStock

同步后的自动重放：

- `--sync-skills` 在复制完成后调用 `patch_vendor_skills.py` 幂等重放全部本地
  技能补丁（脚本 import 修复、旧工具引用改写、preset 随行技能发布）。
- KStock 自有技能 `kstock/skills/*` 会被重放进 `vendor/skills/public/*`
  （上游覆盖不丢失，源头在仓库内）。

## 技能为什么仍是快照

技能是**数据**不是代码：快照换来可离线、可审阅、按技能粒度增删，且
`vendor/skills`（409 文件 / 8.2 MB）体积可控。引擎是**代码**（旧快照形态
9423 文件 / 86.8 MB，且必须构建），所以走分支。两条线形态不同不是不一致，
而是按对象的可再生产物粒度选手段。

## 版本口径

- `upstream.lock.json` 的 `engine.version` 与上游 tag 同号（tag 与
  package.json 同号，如 v3.0.7 ↔ 3.0.7）；早于 3.0.5 的历史快照曾出现
  tag 领先一个号的情况。
- `engine.base_tag`/`engine.base_commit` 记录**基座**，`engine.commit`
  记录**消费态**（= 基座 + 7 个产品提交）。

## 补丁失配即失败

- 技能补丁（`patch_vendor_skills.py`）锚点失配时**响亮失败**：打印失配清单
  并以 1 退出，绝不为了过门禁删除补丁。
- 引擎补丁不再有「重放」这一步：它们固化在 fork 分支上，由
  `scripts/verify_engine_contract.py` 断言（工作树必须等于锁定提交、
  7 处标记必须都在、基线必须是祖先、集成分支不许有裸提交），失配即失败。
